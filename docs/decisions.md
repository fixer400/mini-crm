# Решения и допущения

## Где ТЗ допускает разные трактовки

1. **Роль хранится в `app_metadata`** пользователя Supabase и копируется триггером в `profiles.role`. `user_metadata` пользователь может менять сам, `app_metadata` — нет. Пользователь без роли считается исполнителем: это безопасный вариант по умолчанию.
2. **Смена статуса только через RPC `change_task_status`.** Колонка `status` закрыта для записи правами на уровне колонок. Это надёжнее триггера-проверки на `UPDATE`: обойти его через PostgREST нельзя.
3. **Постановщик не может «взять в работу» за исполнителя.** По ТЗ это делает назначенный исполнитель. Постановщик управляет только проверкой (принять / вернуть).
4. **Статус «Принята» — финальный**, переходов из него нет: по ТЗ «другие переходы запрещены».
5. **Постановщик может редактировать задачу в любом статусе** (название, описание, объект, исполнитель), но не статус. Смена исполнителя не сбрасывает статус и не пишется в историю: в ТЗ история касается только статусов.
6. **Исполнителем назначается только пользователь с ролью «исполнитель».** Это проверяет триггер в базе.
7. **Объект с задачами удалить нельзя** (`on delete restrict`): нужно сначала удалить или перенести задачи. Так задачи не пропадут случайно вместе с объектом.
8. **При удалении задачи удаляется и её история** (каскадом на стороне БД). Через API историю удалить нельзя: это делает только база вместе с задачей. Альтернатива — мягкое удаление задач (см. «Что не успел»).
9. **Ошибка «задача не найдена» и «чужая задача» для исполнителя одинаковая.** Так нельзя узнать, существует ли задача с данным id.
10. **Видимость профилей.** Постановщик видит всех, это нужно для выбора исполнителя. Исполнитель видит себя, авторов своих задач и участников их истории, остальных пользователей — нет.
11. **Комментарий к смене статуса** обязателен при возврате на доработку. В остальных переходах интерфейс его не запрашивает, но RPC его принимает.
12. **Страница «Задачи»:** у исполнителя это «Мои задачи», у постановщика — «Все задачи» по всем объектам (дополнительно к карточкам объектов).
13. **Стартовая страница** у постановщика — список объектов, у исполнителя — «Мои задачи».
14. **Данные тестовых пользователей** создаёт `npm run seed`. Объекты, задачи и все смены статусов он делает через обычный API от имени пользователей. Поэтому история в демо-данных настоящая и прошла все проверки базы.
15. Типы БД (`database.types.ts`) написаны вручную в формате `supabase gen types`, потому что CLI-генерация требует подключения к проекту. При изменении схемы их нужно перегенерировать.

## Что не успел / что бы сделал дальше

- **Мягкое удаление задач** (`deleted_at`), чтобы история сохранялась навсегда.
- **Аудит изменений полей задачи** (кто сменил исполнителя или описание), а не только статусов.
- **Realtime-обновления**: сейчас данные обновляются при действиях и при возврате на вкладку.
- **Пагинация и поиск** по задачам и объектам: на объёмах тестового задания не нужны.
- **pgTAP-тесты** в `supabase/tests` вместо PGlite-скрипта и CI, который их запускает.
- **E2E-тесты интерфейса** (Playwright).
- **Админка пользователей** в интерфейсе: сейчас пользователей создают в панели Supabase.
- Сброс пароля по email.
